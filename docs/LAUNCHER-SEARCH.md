# Launcher search

The shared web launcher searches installed app names, settings destinations and enabled AppAPI capabilities. All Android, Linux and PowOS launcher apps keep name search. AppAPI capabilities require the local App API app/runtime; unavailable providers do not prevent settings or app search.

Native Android settings use the system's `SEARCH_INDEXABLES_PROVIDER` catalog: raw records, XML preferences, dynamic records, and non-indexable-key exclusions. Only system providers and resolvable system destinations are accepted. Results retain their preference key, fragment or direct intent, and breadcrumb. The host stores destination intents privately; the web shell can only open an indexed ID, never submit arbitrary intent extras.

`NativeSettingsIndex` refreshes a process-wide snapshot in a background worker when searched after five minutes, or when the language changes. A completion event refreshes an already-open launcher search. Indexing never runs on the UI thread or on every keystroke; it changes no setting. The root helper is a bounded, read-only invocation from the installed APK, using Android's external-provider query API. Privileged installs with `READ_SEARCH_INDEXABLES` use ContentResolver directly. Root access is used only when PowOS root mode is already enabled, and only for the owner user.

Ordinary unrooted installs cannot read Android's system-only index. They retain resolvable standard page links. There is no generic settings-search result: unmatched text remains available to the launcher chat flow. Coverage means entries published as searchable by the installed OS, not hidden/disabled preferences, private app contents, or controls omitted by the OEM. Provider/app updates are picked up on the next demand-driven cache refresh.

PowOS settings results reveal the named control in the settings scroller after layout settles and retain a theme-colored highlight until interaction. Native links reconstruct the nested preference-argument Bundle at launch (Intent URI serialization drops Bundles). On rooted phones, fragment destinations use a restricted root navigator to Settings.SubSettings because OEM search trampolines reject callers outside their signature allowlist; direct exported destinations retain the normal app launch path. Both carry the preference key so Android can scroll to and highlight the row. Native highlighting still depends on the destination implementing Android’s preference highlighting contract. AppAPI results open the selected app/action in App API, including its existing inputs and confirmation flow. Searching or selecting a result never calls the capability. Disabled apps and actions are omitted. This indexes capability metadata, not every app's private contents.

`shell/search.ts` exports `registerSearchProvider({ id, search(text, signal) })`. A provider returns destinations `{ id, label, source, keywords?, open() }`; it may return a Promise. Return its unregister function when unloading a provider. Observe the abort signal for expensive work. Searches debounce 100 ms, time out providers after 1.8 s, discard old-query responses and show available results immediately. Providers must return only user-visible, authorized entries; discovery must not execute writes. Built-in settings use the same result contract. AppAPI reads `/apps` through the App API app's declared network capability and caches metadata for one minute.

Personal sources (`shell/searchsources.ts`, host side `SearchSources.kt`): the phone's contacts (ContactsContract filter, the main number shown; a tap opens the contact, its Call button opens the dialer) and files (MediaStore by name, newest first; "recent" lists the newest; a tap opens the file in its viewer). The page receives ids and names only; the host rebuilds the contact/file URI and number from the id, so the page cannot open arbitrary URIs. READ_CONTACTS and READ_MEDIA_* are asked once, from an "Allow contacts and files in search" row under other results (never a dialog while typing; rooted: `pm grant`); a refusal is kept. Each source streams in on its own: while it answers, its card shows placeholder rows (`SearchProvider.placeholder`), so there is no blank wait. Quick math and unit conversions (`shell/searchmath.ts`: a tokenizer and recursive-descent parser, never `eval`) show inline as the first answer; a tap copies the value. "Search the web for …" is always the last row (Android's web search, else the browser). Hint rows, placeholders and the web row never count as results: text that finds nothing still becomes the launcher chat. Checks: `node --test shell/test/searchmath.test.ts`; gate scenes `search-sources-{folded,unfolded}` (`shell/dev/search-sources-check.js`, the mock host's contacts and files).

PowOS app pages receive an optional `route: Record<string,string>` prop from `openApp(id, from, route)`. App API accepts `{app, action}` to open a specific capability. Other apps can use this to implement their own result destinations.

Checks: `shell/dev/gate.sh --tree` includes launcher search at mobile and desktop widths. `tools/phone/verify/queue.sh add --dev auto <task> launcher-search.sh` checks the deployed shell and real catalog without executing any capability.
